## What a green gate does not cover

1. **A partial coverage register now, where there was none.**
   `tests/_support/release_criteria.py` classifies the nine chapter-19 elements of this row
   and the nine tier entries that carry them. EIGHT are `CUT`. The ninth is not, and the
   distinction is the serious half: `ui030-honest-metric-rule` is **Tier A**, and
   `MOS-REL-005` forbids cutting Tier A under any circumstance, so it is not cut -- it is
   UNMET, verdict `NONE`, executed by nothing. An earlier draft of this paragraph said all
   nine were cut, which would have converted an uncuttable unmet obligation into a recorded
   and therefore permitted one. See open condition 7. It
   classifies none of the platform or training-pipeline items, so the original sentence still
   stands for them: ten checks pass, and what fraction of section 15.1.2's 0.3.0 contents
   they stand behind is unrecorded for everything the ingestion did not touch. That remainder
   is frozen as a COUNT in `UNREGISTERED_CONTENTS` and `UNREGISTERED_TIERS`, so it can shrink
   and cannot grow.
2. **`zero-core-change` passed while the capability it measured was unreachable in
   production.** This is the most important sentence in this record. The check compares a
   diff's *path set*: `7c1b408` touched only `services/`, `examples/`, `schemas/`,
   `pyproject.toml` and `tests/`, and passed -- while `lung_nodule` could not be submitted,
   resolved, or published against, because four separate places derived the served capability
   set from the platform singleton. Two were fixed in `8734721`; two more, plus the viewer's
   own list, survived that fix and are closed in `7cb0658`. **A path set cannot see
   reachability.** Register entry 68.

   THE MISSING CHECK NOW EXISTS. `capability-reachable` is the tenth check of this row,
   registered through `tests/unit/test_gate_contract.py`'s `LOCAL_EXTRA` -- the only route
   by which `tests/gate/` may hold a module section 15.1.2 does not name, and the same
   route `migration-drift` took after the 0.2.0 gate went green against a database holding
   none of 0.2.0's tables. It asserts, against the DEPLOYED API, worker, registry and
   viewer, that every capability this deployment serves is admitted, resolved, published
   against, executed and offered to a reader. It refuses a `MOS-EXEC-053` replay rather
   than reading back an execution some earlier worker image performed, and it was run
   twice consecutively green to prove that refusal does not make the gate unrepeatable.

   Its own limits, stated because a check believed to cover more than it does is worse
   than an absent one: two of the five properties resolve IN-PROCESS against this
   checkout rather than against the deployment, and the module says which; and the fourth
   of entry 68's assemblies -- `metadata_for`, reached only from
   `medos/training/runs.py`'s `_output_kind_of`, which swallows the `KeyError` -- is not
   exercised by any property.
3. **`MOS-REL-108` was violated by the mechanism written to close register entry 65.** The
   seam read a dotted module path out of `MEDOS_CAPABILITY_PROVIDERS` and called
   `importlib.import_module()` on it, inside both platform processes. `MOS-REL-108` forbids
   dynamic module import without qualification, and `MOS-CONF-109` rests the IEC 62304 section
   4.3 segregation argument on that rule -- "a segregation argument a reviewer can execute
   rather than read". Closed in `7cb0658` by static composition through
   `services/catalogue.py`. Recorded here because it reached a commit, and because the
   Definition-of-Done form of the same rule (item 18) is *qualified* to
   configuration-supplied non-first-party paths where `MOS-REL-108` itself is not -- which is
   how it was missed.
4. **Register entry 65 remains open as a specification gap.** No chapter states how the API
   process and the worker process of one deployment agree on the capability set. The shipped
   mechanism is a declared stand-in for `MOS-SVC-107` registration plus `MOS-REG-072`
   deployment rows and must be REPLACED by them, not extended. Four amendment drafts were
   written this session and all four were refused by their own verification.
5. Register entries 63, 64, 66 and 67 are open imaging-contract defects. Two of them prescribe
   *opposite* fixes for the same symptom and must be settled together, not separately.
6. **The images are unpublished** (see the README).
7. **A Tier A element of this release is in force, vacuously true, and executed by nothing,
   and no response exists for that.** `ui030-honest-metric-rule`. `MOS-UI-365` puts the
   honest-metric display rule "fully in force" at 0.3.0 and `MOS-UI-371`'s Tier A clause
   reaches it: it is a marking obligation on the clinician surface that `MOS-TRAIN-215`,
   `MOS-TRAIN-221` and `MOS-TRAIN-222` already make a MUST. **Measured:** nothing in this
   repository renders a figure drawn from `capability_claims` or `evaluation_runs` -- `web/`
   holds the OHIF extension and its renderer emits job state, series selection, provenance
   fields and stored objects, with no summary card, no list column named for a capability's
   primary metric, no picker tooltip and no export header. So "no selection-partition metric
   appears as headline performance" is satisfied the way an empty set satisfies a universal.
   `MOS-REL-012` is why that is not enough: an unexecuted acceptance criterion means the
   requirement is not satisfied, whatever the code does. `MOS-REL-005` forbids cutting it and
   `MOS-REL-009` offers no response that would, so it is reported as a **release defect**
   rather than retiered, and `headline-partition` is inapplicable because the four SURFACES
   were cut and not because the rule was. **The first surface that renders a figure makes the
   check applicable again, and the `INAPPLICABLE` entry must be deleted and the module
   written in that same change.** **Register entry 73.**
8. **The elements cut above return in 0.4.0 and 0.4.0 is the last row section 15.1.2
   defines.** `MOS-REL-005` makes a cut Tier B item reappear as Tier A or B of the next
   release, so twelve Tier B operator-surface elements -- the model picker, the training
   submit surface, the configuration-search surface, the promotion screen, the refusal
   catalogue, and the seven-member returning set -- are Tier B contents of 0.4.0. A Tier B cut
   taken at 0.4.0 has no next release to reappear in, so `MOS-REL-005`'s return rule becomes
   unsatisfiable rather than deferred. Whether that forces the items into 0.4.0 or forces a
   fifth release row into section 15.1.2 is a decision for the plan's owner and is not taken
   here. **Register entry 75.**
