`--require-stack` turns an unavailable dependency into a failure rather than a skip, so a
skip-heavy green is not reachable from this command. That switch exists because a green run
that had skipped almost everything was reported as a pass on this project four times.

### The run

```
$ pytest -m gate_0_2_0 --require-stack -q
STACK PROBE: 1/1 declared dependencies ready
INFRA SKIPS: 0
DATA SKIPS:  0
ENV SKIPS:   0
OTHER SKIPS: 0
36 passed, 1296 deselected in 23.02s
exit 0
```

Every check above is recorded PASS on the strength of this one run: the exit code
was 0, and `pytest_collection_modifyitems` in `tests/gate/conftest.py` raises
`UsageError` if any check of this row is missing from the selection, so exit 0 cannot
mean "some of them passed". All four skip counts are zero, so it also cannot mean
"some of them did not run".

**Which tree and which deployment.** The run was made at the working tree of this session,
against a deployment REBUILT FROM EMPTY -- all MedicalOS containers and volumes were deleted
and recreated, so Postgres, MinIO and the PACS archive each started with nothing. For a PRIOR
release that is the correct evidence rather than a shortcut: section 15.1.2's 0.3.0 row
requires "0.1.0 and 0.2.0 gates green, PLUS" its own checks, so what has to be true at the
current tree is exactly what was measured. It is NOT evidence that these checks passed at the
commit named in Commit range, and this record does not claim that.

The rebuild was not cosmetic. Before it, this row was RED for a reason that had nothing to do
with rejection handling: the shared PACS had accumulated derived objects across many runs, so
every candidate study for the "present but no eligible series" fixture already held a CT, and
`idempotency-three-surface` counted four minted series where it expects two. `clean_slate`
truncates the job tables and states that the ARCHIVE is not touched -- which is correct for
what it is for, and leaves the archive as the one piece of deployment state no check resets.

## What a green gate does not cover

1. **There is no coverage register for this release.** `tests/_support/release_criteria.py`
   classifies section 15.1.2's contents and 15.1.3's tiers for 0.1.0 only. A green
   `-m gate_0_2_0` therefore states that its six named checks passed and states *nothing*
   about which of this release's contents those checks stand behind. That is exactly the
   condition under which the 0.1.0 gate went green with `MOS-SAFE-089a` unmet -- the defect
   that caused `release_criteria.py` to be written in the first place -- and it is unfixed
   here.
2. **The contents cell may carry the same untiered-item defect as 0.1.0.** Register entry 61
   asks in terms that "the 0.2.0 row should be checked for the same defect before the tag". A
   check run this session found **three contents items with no exact tier match**, including
   the whole Chapter 17 training-pipeline clause. Not closed. The chapter-19 ingestion did not
   reintroduce it: every element it added carries exactly one tier and
   `test_every_ingested_contents_item_carries_exactly_one_tier_row` asserts that mechanically.
3. **A Tier A element of this release is HALF BUILT, and no response exists for that.**
   `ui020-ruo-badge-and-research-gating`. `MOS-UI-346` has two halves. The **badge** exists:
   `render.js` emits `medos-ruo` with the `clinical_use_mode` whenever the view carries one.
   The **gating** does not, on either side -- **measured:** the string `include_research`
   occurs nowhere in `medos/`, `web/` or `tests/`, so the query parameter `MOS-UI-346`
   requires alongside `result.read.research` is not implemented, not served and not asserted.
   Today the omission is masked rather than harmless: no surface renders a result list at
   all, so there is nothing for a research result to leak into. **The first list shipped is
   the first list that defaults research results into a clinician's view**, which is the
   failure `MOS-SAFE-041` exists for. This row's `ruo-marking` check covers the DICOM writer
   refusing to emit an unmarked object and says nothing about either half. `MOS-REL-005`
   forbids cutting it and `MOS-REL-009` offers no response that would, so it is reported as a
   **release defect** rather than retiered. **Register entry 73.**
4. **There is now a partial coverage register for this release.**
   `tests/_support/release_criteria.py` classifies the nine chapter-19 elements of this row
   and the nine tier entries that carry them. It classifies none of the evidence-plane or
   training-pipeline items; that remainder is frozen as a COUNT in `UNREGISTERED_CONTENTS`
   and `UNREGISTERED_TIERS`, so it can shrink and cannot grow, and gap 1 above stands for
   everything it does not name.
5. Register entries 26-62 record 37 specification defects found while building this release,
   each resolved in code and open in the text.
6. **The images are unpublished** (see the README).
