`--require-stack` turns an unavailable dependency into a failure rather than a skip, so a

that had skipped almost everything was reported as a pass on this project four times.

### The run

```
$ pytest -m gate_0_1_0 --require-stack -q
STACK PROBE: 7/7 declared dependencies ready
INFRA SKIPS: 0
DATA SKIPS:  0
ENV SKIPS:   0
OTHER SKIPS: 0
24 passed, 1308 deselected in 76.61s
exit 0
```

Every check above is recorded PASS on the strength of this one run: the exit code
was 0, and `pytest_collection_modifyitems` in `tests/gate/conftest.py` raises
`UsageError` if any check of this row is missing from the selection, so exit 0 cannot
mean "some of them passed". All four skip counts are zero, so it also cannot mean
"some of them did not run".

**Which tree and which deployment.** The run was made at the working tree of this session,
against a deployment REBUILT FROM EMPTY -- all MedicalOS containers and volumes were deleted
and recreated, so Postgres, MinIO and the PACS archive each started with nothing. For a PRIOR
release that is the correct evidence rather than a shortcut: section 15.1.2's 0.3.0 row
requires "0.1.0 and 0.2.0 gates green, PLUS" its own checks, so what has to be true at the
current tree is exactly what was measured. It is NOT evidence that these checks passed at the
commit named in Commit range, and this record does not claim that.

The rebuild was not cosmetic. Before it, this row was RED for a reason that had nothing to do
with rejection handling: the shared PACS had accumulated derived objects across many runs, so
every candidate study for the "present but no eligible series" fixture already held a CT, and
`idempotency-three-surface` counted four minted series where it expects two. `clean_slate`
truncates the job tables and states that the ARCHIVE is not touched -- which is correct for
what it is for, and leaves the archive as the one piece of deployment state no check resets.

## What a green gate does not cover

1. **Six contents items carry no tier.** `MOS-REL-005` requires exactly one each, and
   section 15.3's conformance item 1 says a parser "fails if any contents item has no tier":
   `gateway-and-deid`, `triage-and-series-selector`, `job-and-queue-driver`,
   `vendored-lung-segmentation`, `api-key-auth`, `single-triton-docker-compose`. The
   repository already reports this on every gate run as `UNTIERED_CONTENTS`. **Register entry
   61.** An attempt to close it this session was refused by its own verification: the proposed
   assignments turned `tests/unit/test_release_criteria.py` red, and two of them would have
   created uncuttable Tier A items with no gate check -- the one thing that register's
   frozen-debt device exists to prevent. It is open on purpose rather than closed badly.
2. **Thirteen Tier A items have no gate coverage.** Three are the originals -- `audit`,
   `tier-a-append-only-audit`, `tier-a-gateway-sole-credential-holder`. Ten arrived with the
   chapter-19 ingestion and are not ten new gaps: each was already uncovered inside a chapter
   whose placements section 15.1.2 had never read. Recorded and frozen in
   `TIER_A_WITHOUT_GATE_COVERAGE`; a fourteenth is a test failure. `MOS-REL-005` makes Tier A
   uncuttable, so none of these can be resolved by cutting them.
3. **A Tier A element of this release is NOT BUILT, and no response exists for that.**
   `ui010-safe012-adjacency-set`. `MOS-UI-345` requires all five members of the
   `MOS-SAFE-012` set -- `service_id`, the `ServiceVersion`, `legal_manufacturer.name`, the
   producing deployment's `clinical_use_mode` and the `Result`'s `review_status` -- adjacent
   to the finding, in the initial render, with zero interaction. **Measured:**
   `legal_manufacturer` and `review_status` occur nowhere under `web/`.
   `provenance.js`'s `REQUIRED_JOB_FIELDS` carries `service_id` and `service_version` and
   `render.js` carries `clinical_use_mode`; the other two are absent from the field lists,
   from the renderer, and therefore from
   `test_the_panels_required_field_list_matches_what_the_api_returns`, which parses those
   lists -- so the one check that would notice is checking a list that does not name them.
   `MOS-SAFE-053` puts both fields at the top level of the `Result` precisely so a client
   cannot omit the marking by accident. This is a **release defect**: `MOS-REL-005` forbids
   cutting it and `MOS-REL-009` offers no response that would, so it is reported rather than
   retiered. **Register entry 73.**
4. **The clinician surface's four-channel and three-part refusal obligations are Tier A and
   are verified outside every gate row.** `tests/e2e/test_demo.py::test_rejected_renders_`
   `visually_distinct_from_failed` covers both, structurally, by reading the served
   `render.js` and `styles.css`. Chapter 19's acceptance check 2 asks for both states
   rendered with the stylesheet **disabled** and again in a greyscale-forced profile;
   neither arm exists anywhere in this repository, so a stylesheet that failed to load would
   leave the CSS assertions green and the reader with two identical grey boxes.
5. **De-identification is refused, not implemented.** `medos/gateway/app.py` returns 503
   `DEID_NOT_IMPLEMENTED` for the consumer classes that require it, and no test exercises that
   refusal. The contents cell names "DICOM Gateway + de-identification" as a single item, so
   the item is half delivered and the gate's verdict for it covers the other half.
6. **The images are unpublished** (see the README).
