# Аудит: `medlange/core` (`medos.sdk`) как самостоятельный SDK для медсервиса

Дата аудита: 2026-10-04. Объект: `D:/PycharmProjects/medlange/core`, пакет `medos/medos/sdk/` (~5 900 строк) + адаптеры + профили + cookbook. Прогнан сьют SDK-модулей: 48 тестов зелёных (sdk_profiles, modelcard, pipeline, bus, cookbook, result_writer, purity gate).

## 0. Что это сейчас по факту

SDK — это **sub-package внутри одного wheel с платформой**, а не отдельный артефакт. `pyproject.toml:9-30`: дистрибутив `medos` 0.1.0.dev0; различие SDK/платформа — только на уровне extras (`pip install medos` = numpy/pydicom/highdicom/pyyaml; `medos[server]` = +psycopg/FastAPI/requests). В wheel лежат все 165 модулей платформы (api, db, evidence, worker…). Граница чистоты держится не упаковкой, а AST-гейтом `tests/unit/test_shared_package_is_pure.py:155` (SDK может тянуть только pure core `medos.core.*` + лениво — `medos.dicomweb/inference/writer/capabilities`). В PyPI пакета нет — `docs/ROADMAP.md:61` («PyPI — ещё нет»), ставится только из git. Продуктовый статус честно зафиксирован в `docs/spec/99-known-inconsistencies.md:373` (запись 151: спецификация до сих пор описывает старый продукт-платформу, «SDK-first re-chaptering owed»).

## 1. Полнота SDK для production-сервиса

Есть и работает (с live-доказательствами): пайплайн fetch→canonical volume→chain→infer→postprocess (`sdk/pipeline.py`), CT-only дефолт с записанными исключениями (`pipeline.py:184-204`), DICOMweb QIDO/WADO/STOW клиент с правильной обработкой DICOM JSON Model и FailedSOPSequence (`medos/dicomweb/client.py`), SEG/SR через единый writer (`sdk/adapters/results.py`), два режима драйвера (`sdk/runtime.py`), профили с закрытой схемой и отказами словарём (`sdk/profiles.py`), kafka/rabbit драйверы + schema-flexible codec (`sdk/adapters/bus.py`), CLI с batch-дисциплиной (`sdk/__main__.py:52-73`).

Чего нет для production (проверено grep'ом по `medos/sdk`: ни одного хита на retry/backoff/DLQ/prometheus):

| Область | Состояние | Куда смотреть |
|---|---|---|
| Ретраи/backoff | Нет. `TritonBackend.infer` — «NO RETRIES HERE» by design (`medos/inference/triton.py:31`); bus-драйверы без повторов публикации | `sdk/adapters/bus.py:264-268` |
| DLQ / poison messages | **Дефект**: `decode_request` (CodecError на битом сообщении) стоит ВНЕ try (`sdk/runtime.py:86-106`), но `ack()` в `finally` коммитит offset → битое сообщение **убивает воркер и при этом коммитится** = потеря. Без error-топика исключение тоже ack'ается в finally и переподнимается — сообщение потеряно и цикл мёртв. Противоречит собственному docstring «a crash mid-study re-delivers» | `sdk/runtime.py:83-107` |
| Дедупликация/идемпотентность | Нет на всех уровнях. `PlatformWriter` передаёт `expected_idempotency_key=None` (`sdk/adapters/results.py:266`), хотя платформенный `build_job_identity` умеет derive-UID из ключа и сам документирует цену «duplicated series per crash, forever» | `medos/writer/identity.py:538-560` |
| Аутентификация/тенанты | Только bearer-token к PACS. `tenant_id`/`clinical_use_mode` в writer — **печатаются в DICOM**, не enforce'атся. AuthN/Z модели у SDK нет в принципе | `sdk/adapters/results.py:202-205`, `sdk/profiles.py:189-205` |
| Наблюдаемость | Только download/process-тайминги на результате и JSON-lines в stdout. Ни logging, ни метрик в sdk/ | `sdk/runtime.py`, `sdk/__main__.py` |
| Многомодельность | Профиль биндит ровно одну card; `model_id` из входящего bus-сообщения **молча игнорируется** — воркер гонит карточку профиля | `sdk/runtime.py:88-90` vs `bus.py:189-208` |
| GPU-оркестрация | Нет и не должна быть — вся мощь платформы (residency, §13.10, `medos/inference/residency.py`) вне SDK. Внешний режим = «принеси свой KServe v2» | `sdk/adapters/inference.py:98-148` |
| Горизонтальное масштабирование | Consumer group Kafka — да (несколько инстансов одного профиля). Local mode — один процесс, синхронно | `sdk/runtime.py:57-61` |
| Тестируемость | Сильная сторона: phantom + pinned hashes (`sdk/fixtures.py`), selftest card, injectable volume_builder/select_series/sink, 48 зелёных юнит-тестов, gate на чистоту закрытия | `tests/unit/test_shared_package_is_pure.py` |

## 2. Сторонний разработчик: путь «своя КТ-модель, свой PACS, SEG обратно»

Прогнал путь по коду и по evidence-скриптам в `D:/PycharmProjects/e2e-staging/` (вне репо, но это и есть подлинные прогоны cookbook).

**За день получится:**
- Установка из git + профиль против своего DICOMweb-PACS — да. Клиент generic (QIDO/WADO/STOW, `medos/dicomweb/client.py`), tenant-префикс в `base_url` — просто часть URL. Секреты через `token_env` (`sdk/profiles.py:144-151`). Отказы профиля — читаемым словарём, cookbook честный: `medos/examples/profiles/README.md`.
- Local-режим fetch→preprocess→findings — да, pattern доказан (`e2e-staging/c3-local/profile.yaml`, embedded-скрипт).
- Bus-режим (Kafka, свой словарь сообщений) — да, доказан на живом стеке (`c4-cookbook`, `mosmed.yaml`); правило «fields: внешний ключ → каноническое поле» укусит ровно один раз и диагнозом (`CodecError`).

**Упрётся в стену:**
1. **Карточка от штатного трейнера не пишется обратно в PACS.** Трейнер пишет outputs только `{kind, value, name}` (`trainer/medos_trainer/packaging.py:505-509`), а `PlatformWriter` отказывает без `structure` slug — по имени (`sdk/adapters/results.py:60-66`, тест `tests/unit/test_result_writer.py:51`). Все live-e2e записи SEG (C1b) использовали **ручную** карточку с `structure: lung_right/lung_left` (`e2e-staging/writer_live_e2e.py:66-79`). ROADMAP это знает («схема карточки 1.1 с кодами понятий», `docs/ROADMAP.md:101`), но формат всё ещё pinned ровно `medlange.modelcard/1` (`sdk/modelcard.py:49`), и трейнер 1.1 не пишет. Плюс словарь понятий — платформенный JSON (десятка записей: lung_right, heart, esophagus…), расширение через недокументированный `MEDOS_CAPABILITY_CONCEPTS` (`medos/capabilities/base.py:283`).
2. **Реальный served-модельный путь не прогнан ни разу.** Все live-e2e (C3, C4, C1b) — `EmbeddedInference`-заглушки. `KServeV2Inference` применяет chain клиентом и шлёт **полный тензор** одним запросом, без sliding-window, без inverse-mapping в source grid (`sdk/adapters/inference.py:128-148`): контракт писателя требует mask на source grid (`sdk/adapters/results.py:104-113`), а обратного преобразования в SDK нет (`first_patch` есть, клиентского окна и обратной resample — нет, `sdk/preprocess.py:843`). Модель тренера патч-базирована; Triton-репозиторий из `deploy_model.py` описывает patch-размерность. Итого: kserve_v2 + реальная модель + writer = shape/grid refusal — первым это узнает сам сторонник.
3. bspline3 не исполняется в numpy-executorе (refused by design, `sdk/preprocess.py:41-50`) — серверный runtime обязан, это надо понимать при самодельной модели.
4. MR/PT — только `select_series: image_only` из профиля; свой селектор = код, не YAML.
5. Повторный прогон батча → **дубли SEG/SR** в архиве (п.1 таблицы выше).

## 3. Связность с платформой

Ленивые достижения SDK в платформу (разрешены гейтом `ADAPTER_ALLOWED`, `test_shared_package_is_pure.py:96`): `medos.dicomweb.client` (pacs.py:90), `medos.inference.triton` (inference.py:113), `medos.capabilities` + `medos.core.bundle` + `medos.writer.*` (results.py:208-213), `medos.core.geometry` (pipeline.py:165).

Оценка: **для инференс/PACS-слоёв — норма** (это и есть «adopt, не build», драйверы — тонкие мосты, повторная реализация SEG запрещена собственным правилом MOS-IMG-003). **Для writer — ограничение**: концепт-словарь и `medos.writer` несут клинико-правовую семантику (tenant, clinical_use_mode, коды по MOS-IMG-112 «never invent a code»), т.е. SDK-страна без платформы умеет findings, но не умеет клинически подписанные DICOM-объекты — и это осознанный правовой дизайн, а не случайность. Проблема не связность, а то, что граница держится тестом, а не артефактом: wheel содержит платформу целиком, грань проедет любой импорт выше pure core, и тест это словит — но сторонний потребитель получает 160 лишних модулей и соблазн.

## 4. Карточка модели и трейнер

`medlange.modelcard/1` (`sdk/modelcard.py`): model_id/version, spec-документ + sha256 дайджест (верифицируется при load, `modelcard.py:176-185`), weights{path, weights_file, format, digest, onnx_*}, frameworks, outputs, stamp. Хорошо: digest спека, отказ на чужом формате, «parse is the validation».

Для независимых производителей **недостаточно**:
- Формат существует только как код + docstrings: **ноль упоминаний** в MEDICALOS_SPEC.md, нет JSON-Schema в `medos/schemas/` (там evidence/lung-nodule/training). Спека препроцессинга, напротив, нормативно расписана (`docs/spec/04-imaging-contracts.md:410`, MOS-IMG-049).
- Нет клинической метадаты: intended use, показания/противопоказания, популяция, метрики качества, лицензия, provenance данных. Для research-пайплайна ок, для «независимого производителя» как документа о модели — тонко.
- `ModelCard.load` проверяет digest **спека**, но не digest весов против файлов (только существование каталога, `modelcard.py:187-195`); обещание «о байтах» для weights не замыкается читателем (проверяет только `deploy_model.py`).
- Outputs-описатель говорит лишь segmentation+measurement (`sdk/postprocess.py:72-121`); detection/bbox/классификация — не говорит, хотя платформа имеет детекцию (`trainer/medos_trainer/detection.py`). И найденный в примерах lung-nodule — это platform capability, а не card-driven SDK-сервис.

## 5. Вердикт

**Готовность как SDK для сторонних медсервисов: 4/10.**

Обоснование: инженерная дисциплина контрактов, отказов-словарей, closed-schema конфигов, чистоты closure и доказуемости (cookbook с подлинными выводами, живые e2e, гейты) — уровня зрелого фрейдворка, это редкость. Но как продукт для чужой production-эксплуатации: не опубликован, один процесс = одна модель, нет ретраев/DLQ/идемпотентности (есть ack-потеряющий дефект), нет наблюдаемости, нет auth-модели, writer-контур не сомкнут с собственным трейнером, единственный прогнанный inference-путь — встроенная заглушка. Для research-интеграций «PACS→модель→SEG» в контуре одного деплоя — рабочий, честный 6/10; для клинического много-тенантного сервиса — 3/10.

**Топ-5 доработок (с файлами):**

1. **Живучесть bus-контура + идемпотентность записи.** Исправить ack-семантику `ExternalWorker.run_once` (не коммитить при CodecError/при отсутствии error-топика; poison → error topic или DLQ), добавить backoff в `run_forever`; провести стабильный idempotency-key до `PlatformWriter` (`expected_idempotency_key` сейчас всегда None). Файлы: `medos/medos/sdk/runtime.py:83-107`, `medos/medos/sdk/adapters/bus.py:240-268`, `medos/medos/sdk/adapters/results.py:255-267`, опора `medos/medos/writer/identity.py:538-560`.
2. **Card 1.1 + опубликованная схема.** Трейнер пишет `structure`/`concept_key` (словарь структур — из binding/спека), формат `medlange.modelcard/1` расписать нормативно (JSON Schema в `medos/schemas/` + раздел в docs/spec), верификация digest весов в `ModelCard.load`. Файлы: `trainer/medos_trainer/packaging.py:495-509`, `medos/medos/sdk/modelcard.py:139-212`, `medos/schemas/`.
3. **Прогнать и починить реальный kserve_v2-путь:** клиентский sliding-window поверх `first_patch`/обратное отображение в source grid (сейчас — весть объём одним запросом и ни к чему не приводящий результат), e2e против Triton-репозитория из `deploy_model.py`. Файлы: `medos/medos/sdk/adapters/inference.py:128-148`, `medos/medos/sdk/preprocess.py:843-895`.
4. **Многомодельность и наблюдаемость.** Либо маршрутизация по `model_id` заявки, либо отказ при mismatch (сейчас — молчаливое игнорирование); structured logging + опциональные Prometheus-счётчики в воркерах/CLI. Файлы: `medos/medos/sdk/runtime.py:83-135`, `medos/medos/sdk/__main__.py`.
5. **Публикация и упаковка.** PyPI-релиз (C3 формально ✅, но «PyPI — ещё нет»), осмысленный SDK-only install (сейчас wheel тащит платформу, граница — только AST-гейт), включение `medos/examples/profiles/` в sdist. Файлы: `pyproject.toml:9-31,133-183`, `docs/ROADMAP.md`.

## 6. Сравнение (коротко)

| | **medos.sdk** | **MONAI Deploy** | **Kaapana** |
|---|---|---|---|
| Фокус | контракт «карточка→пайплайн→SEG/SR» + адаптеры к чужой инфраструктуре | исполнение графов операторов (MAP/DAG) поверх DICOM | платформа-стек (OpenStack-подобный) на Orthanc/airflow |
| DICOM-запись результатов | да, единый writer + концепт-словарь | минимальная (чаще отдаёт наружу) | да, через OHIF/DICOM-утилиты |
| Шина/внешние схемы | schema-flexible mapping (сильная сторона) | нет (gRPC/HTTP свои) | airflow/triggers |
| Production-механика (ретраи, DLQ, leases) | нет | частично (исполнители) | да (airflow) |
| Зрелость экосистемы | 0.1.0.dev0, не опубликован | зрелый, но проект свёрнут (2025) | зрелый, DKFZ-backed |
| GPU/оркестрация | нет (делегирует KServe v2) | нет | Kubernetes-нативный |

Позиционирование честное: medos.sdk — не конкурент Kaapana по оркестрации, а тонкий, контрактно-жёсткий слой «модель как данные» (карточка + спека + канонический дайджест) с адаптерами — ниши, где у MONAI Deploy был самый слабый результат (запись в архив, внешние bus-схемы, воспроизводимость препроцессинга), и где у Kaapana лишний вес. При закрытии топ-5 это становится самостоятельным продуктом; сейчас — качественный интеграционный фреймворк исследовательского контура со следами недавней смены личности (платформа→SDK), о которых репозиторий сам честно предупреждает.
