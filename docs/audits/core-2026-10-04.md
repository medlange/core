# Audit: `medlange/core` (`medos.sdk`) as a standalone SDK for a medical service

Audit date: 2026-10-04. Subject: `D:/PycharmProjects/medlange/core`, package `medos/medos/sdk/` (~5,900 lines) + adapters + profiles + cookbook. The SDK module test suite was run: 48 tests green (sdk_profiles, modelcard, pipeline, bus, cookbook, result_writer, purity gate).

## 0. What it actually is today

The SDK is a **sub-package inside a single wheel together with the platform**, not a separate artifact. `pyproject.toml:9-30`: the `medos` 0.1.0.dev0 distribution; the SDK/platform distinction exists only at the level of extras (`pip install medos` = numpy/pydicom/highdicom/pyyaml; `medos[server]` = +psycopg/FastAPI/requests). The wheel contains all 165 platform modules (api, db, evidence, worker…). The purity boundary is held not by packaging but by the AST gate `tests/unit/test_shared_package_is_pure.py:155` (the SDK may pull in only the pure core `medos.core.*` + lazily — `medos.dicomweb/inference/writer/capabilities`). There is no PyPI package — `docs/ROADMAP.md:61` ("PyPI — not yet"), installable only from git. The product status is honestly recorded in `docs/spec/99-known-inconsistencies.md:373` (entry 151: the specification still describes the old platform product, "SDK-first re-chaptering owed").

## 1. SDK completeness for a production service

Present and working (with live evidence): the fetch→canonical volume→chain→infer→postprocess pipeline (`sdk/pipeline.py`), CT-only default with recorded exceptions (`pipeline.py:184-204`), DICOMweb QIDO/WADO/STOW client with correct handling of the DICOM JSON Model and FailedSOPSequence (`medos/dicomweb/client.py`), SEG/SR through a single writer (`sdk/adapters/results.py`), two driver modes (`sdk/runtime.py`), profiles with a closed schema and dictionary-based refusals (`sdk/profiles.py`), kafka/rabbit drivers + schema-flexible codec (`sdk/adapters/bus.py`), CLI with batch discipline (`sdk/__main__.py:52-73`).

What is missing for production (verified by grepping `medos/sdk`: not a single hit for retry/backoff/DLQ/prometheus):

| Area | Status | Where to look |
|---|---|---|
| Retries/backoff | None. `TritonBackend.infer` — "NO RETRIES HERE" by design (`medos/inference/triton.py:31`); bus drivers do not retry publication | `sdk/adapters/bus.py:264-268` |
| DLQ / poison messages | **Defect**: `decode_request` (CodecError on a corrupt message) sits OUTSIDE the try (`sdk/runtime.py:86-106`), but `ack()` in `finally` commits the offset → a corrupt message **kills the worker and is still committed** = loss. Without an error topic, the exception is also acked in finally and re-raised — the message is lost and the loop is dead. Contradicts the code's own docstring "a crash mid-study re-delivers" | `sdk/runtime.py:83-107` |
| Deduplication/idempotency | None at any level. `PlatformWriter` receives `expected_idempotency_key=None` (`sdk/adapters/results.py:266`), even though the platform's `build_job_identity` can derive a UID from the key and itself documents the cost "duplicated series per crash, forever" | `medos/writer/identity.py:538-560` |
| Authentication/tenants | Bearer token to PACS only. `tenant_id`/`clinical_use_mode` in the writer are **printed into DICOM**, not enforced. The SDK has no AuthN/Z model at all | `sdk/adapters/results.py:202-205`, `sdk/profiles.py:189-205` |
| Observability | Only download/process timings on the result and JSON-lines to stdout. Neither logging nor metrics in sdk/ | `sdk/runtime.py`, `sdk/__main__.py` |
| Multi-model | A profile binds exactly one card; `model_id` from the incoming bus message is **silently ignored** — the worker runs the profile's card | `sdk/runtime.py:88-90` vs `bus.py:189-208` |
| GPU orchestration | None, and rightly so — the entire platform power (residency, §13.10, `medos/inference/residency.py`) is outside the SDK. External mode = "bring your own KServe v2" | `sdk/adapters/inference.py:98-148` |
| Horizontal scaling | Kafka consumer group — yes (multiple instances of one profile). Local mode — a single process, synchronous | `sdk/runtime.py:57-61` |
| Testability | Strong side: phantom + pinned hashes (`sdk/fixtures.py`), selftest card, injectable volume_builder/select_series/sink, 48 green unit tests, purity-closure gate closed | `tests/unit/test_shared_package_is_pure.py` |

## 2. Third-party developer: the "own CT model, own PACS, SEG back" path

I ran the path through the code and through the evidence scripts in `D:/PycharmProjects/e2e-staging/` (outside the repo, but these are the authentic cookbook runs).

**Achievable in a day:**
- Install from git + profile against your own DICOMweb PACS — yes. The client is generic (QIDO/WADO/STOW, `medos/dicomweb/client.py`), the tenant prefix in `base_url` is just part of the URL. Secrets via `token_env` (`sdk/profiles.py:144-151`). Profile refusals come as a readable dictionary, the cookbook is honest: `medos/examples/profiles/README.md`.
- Local mode fetch→preprocess→findings — yes, pattern proven (`e2e-staging/c3-local/profile.yaml`, embedded script).
- Bus mode (Kafka, your own message dictionary) — yes, proven on a live stack (`c4-cookbook`, `mosmed.yaml`); the "fields: external key → canonical field" rule will bite exactly once and with a diagnosis (`CodecError`).

**Will hit a wall:**
1. **The card from the stock trainer does not write back to PACS.** The trainer writes outputs only as `{kind, value, name}` (`trainer/medos_trainer/packaging.py:505-509`), and `PlatformWriter` refuses without a `structure` slug — by name (`sdk/adapters/results.py:60-66`, test `tests/unit/test_result_writer.py:51`). All live-e2e SEG records (C1b) used a **manual** card with `structure: lung_right/lung_left` (`e2e-staging/writer_live_e2e.py:66-79`). The ROADMAP knows this ("card schema 1.1 with concept codes", `docs/ROADMAP.md:101`), but the format is still pinned to exactly `medlange.modelcard/1` (`sdk/modelcard.py:49`), and the trainer does not write 1.1. Plus the concept dictionary is a platform JSON (about a dozen entries: lung_right, heart, esophagus…), extended through the undocumented `MEDOS_CAPABILITY_CONCEPTS` (`medos/capabilities/base.py:283`).
2. **The real served-model path has never been run.** All live-e2e (C3, C4, C1b) are `EmbeddedInference` stubs. `KServeV2Inference` applies the chain on the client side and sends the **full tensor** in a single request, with no sliding window and no inverse mapping to the source grid (`sdk/adapters/inference.py:128-148`): the writer's contract requires a mask on the source grid (`sdk/adapters/results.py:104-113`), and the SDK has no inverse transform (`first_patch` exists, but there is no client-side window or inverse resampling — `sdk/preprocess.py:843`). The trainer's model is patch-based; the Triton repository from `deploy_model.py` describes patch dimensionality. Net result: kserve_v2 + real model + writer = shape/grid refusal — the adopter finds this out first.
3. bspline3 does not execute in the numpy executor (refused by design, `sdk/preprocess.py:41-50`) — the server runtime is mandatory; this must be understood when building a custom model.
4. MR/PT — only `select_series: image_only` from the profile; a custom selector is code, not YAML.
5. Re-running a batch → **duplicate SEG/SR** in the archive (item 1 in the table above).

## 3. Coupling with the platform

The SDK's lazy reach into the platform (permitted by the gate `ADAPTER_ALLOWED`, `test_shared_package_is_pure.py:96`): `medos.dicomweb.client` (pacs.py:90), `medos.inference.triton` (inference.py:113), `medos.capabilities` + `medos.core.bundle` + `medos.writer.*` (results.py:208-213), `medos.core.geometry` (pipeline.py:165).

Assessment: **for the inference/PACS layers — normal** (this is precisely "adopt, not build", the drivers are thin bridges, and a second SEG implementation is forbidden by its own rule MOS-IMG-003). **For the writer — a limitation**: the concept dictionary and `medos.writer` carry clinical-legal semantics (tenant, clinical_use_mode, codes per MOS-IMG-112 "never invent a code"), i.e. an SDK country without the platform can do findings but cannot produce clinically signed DICOM objects — and this is a deliberate legal design, not an accident. The problem is not the coupling but that the boundary is held by a test rather than by an artifact: the wheel contains the entire platform, any import above pure core breaks the boundary, and the test catches it — but a third-party consumer gets 160 extra modules and the temptation.

## 4. Model card and the trainer

`medlange.modelcard/1` (`sdk/modelcard.py`): model_id/version, spec document + sha256 digest (verified on load, `modelcard.py:176-185`), weights{path, weights_file, format, digest, onnx_*}, frameworks, outputs, stamp. Good: spec digest, refusal on a foreign format, "parse is the validation".

Insufficient for independent manufacturers:
- The format exists only as code + docstrings: **zero mentions** in MEDICALOS_SPEC.md, no JSON-Schema in `medos/schemas/` (which holds evidence/lung-nodule/training). The preprocessing spec, by contrast, is normatively spelled out (`docs/spec/04-imaging-contracts.md:410`, MOS-IMG-049).
- No clinical metadata: intended use, indications/contraindications, population, quality metrics, license, data provenance. Fine for a research pipeline; thin as a "manufacturer-independent" model document.
- `ModelCard.load` verifies the **spec** digest but not the weight digests against the files (only directory existence, `modelcard.py:187-195`); the "about the bytes" promise for weights is not closed by the reader (only `deploy_model.py` checks it).
- The outputs descriptor speaks only of segmentation+measurement (`sdk/postprocess.py:72-121`); detection/bbox/classification — not spoken of, even though the platform has detection (`trainer/medos_trainer/detection.py`). And the lung-nodule found in the examples is a platform capability, not a card-driven SDK service.

## 5. Verdict

**Readiness as an SDK for third-party medical services: 4/10.**

Rationale: the engineering discipline of contracts, dictionary refusals, closed-schema configs, closure purity, and provability (cookbook with authentic outputs, live e2e, gates) is at the level of a mature framework — that is rare. But as a product for someone else's production operation: unpublished, one process = one model, no retries/DLQ/idempotency (there is an ack-losing defect), no observability, no auth model, the writer loop is not closed with its own trainer, and the only inference path ever run is the embedded stub. For research integrations "PACS→model→SEG" within a single deployment — a working, honest 6/10; for a clinical multi-tenant service — 3/10.

**Top-5 improvements (with files):**

1. **Bus-loop resilience + write idempotency.** Fix the ack semantics of `ExternalWorker.run_once` (do not commit on CodecError / when there is no error topic; poison → error topic or DLQ), add backoff to `run_forever`; thread a stable idempotency key through to `PlatformWriter` (`expected_idempotency_key` is currently always None). Files: `medos/medos/sdk/runtime.py:83-107`, `medos/medos/sdk/adapters/bus.py:240-268`, `medos/medos/sdk/adapters/results.py:255-267`, support `medos/medos/writer/identity.py:538-560`.
2. **Card 1.1 + published schema.** The trainer writes `structure`/`concept_key` (structure dictionary — from binding/spec), format `medlange.modelcard/1` spelled out normatively (JSON Schema in `medos/schemas/` + a section in docs/spec), weight digest verification in `ModelCard.load`. Files: `trainer/medos_trainer/packaging.py:495-509`, `medos/medos/sdk/modelcard.py:139-212`, `medos/schemas/`.
3. **Run and fix the real kserve_v2 path:** client-side sliding window on top of `first_patch`/inverse mapping to the source grid (currently the whole volume in one request and a result that leads nowhere), e2e against the Triton repository from `deploy_model.py`. Files: `medos/medos/sdk/adapters/inference.py:128-148`, `medos/medos/sdk/preprocess.py:843-895`.
4. **Multi-model support and observability.** Either routing by request `model_id`, or refusal on mismatch (currently — silent ignoring); structured logging + optional Prometheus counters in workers/CLI. Files: `medos/medos/sdk/runtime.py:83-135`, `medos/medos/sdk/__main__.py`.
5. **Publication and packaging.** PyPI release (C3 formally ✅, but "PyPI — not yet"), a meaningful SDK-only install (the wheel currently drags the platform along; the boundary is only an AST gate), inclusion of `medos/examples/profiles/` in the sdist. Files: `pyproject.toml:9-31,133-183`, `docs/ROADMAP.md`.

## 6. Comparison (short)

| | **medos.sdk** | **MONAI Deploy** | **Kaapana** |
|---|---|---|---|
| Focus | contract "card→pipeline→SEG/SR" + adapters to foreign infrastructure | operator graph execution (MAP/DAG) on top of DICOM | platform stack (OpenStack-like) on Orthanc/airflow |
| DICOM result writing | yes, single writer + concept dictionary | minimal (usually hands off outward) | yes, via OHIF/DICOM utilities |
| Bus/external schemas | schema-flexible mapping (strong side) | none (own gRPC/HTTP) | airflow/triggers |
| Production mechanics (retries, DLQ, leases) | none | partially (executors) | yes (airflow) |
| Ecosystem maturity | 0.1.0.dev0, unpublished | mature, but the project was wound down (2025) | mature, DKFZ-backed |
| GPU/orchestration | none (delegates to KServe v2) | none | Kubernetes-native |

The positioning is honest: medos.sdk is not a Kaapana competitor in orchestration but a thin, contract-rigid "model as data" layer (card + spec + canonical digest) with adapters — niches where MONAI Deploy had its weakest results (archive writing, external bus schemas, preprocessing reproducibility), and where Kaapana is excess weight. Closing the top-5 turns this into a standalone product; today it is a quality integration framework for the research loop with traces of a recent identity change (platform→SDK), which the repository itself honestly warns about.
