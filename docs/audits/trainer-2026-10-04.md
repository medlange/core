# Аудит `trainer/` (medos-trainer) как самостоятельного продукта

## 0. Состояние репозитория — ключевой факт

Весь «фреймворковый» слой — **незакоммичен** (parked peer-session):

- **Tracked (коммиты до `e587315`)**: `backend.py`, `masked.py`, `masked_trainer.py`, `packaging.py`, `environment.py`, `stamp.py`, `__main__.py`, `Dockerfile`, 3–4 тестовых файла.
- **Untracked (новая работа)**: `plan.py`, `port.py`, `nets.py`, `detection.py`, `overlap.py`, `evidence.py`, `architectures.py`, `training.py`, `tools/ab_evaluate.py`, `tests/fixtures/`, 12 новых тестовых файлов, `LICENSE`.

Вывод по «мусору»: **мусора нет, но интеграция неравномерная** (см. §5).

## 1. Что реально работает

**Запускал сам** (Windows, `.venv` с torch 2.7.1+cpu, nnunetv2, monai 1.5.2):

```
cd trainer && pytest tests          # 417 passed in 59.58s, 0 skips
python -m medos_trainer --help      # plan | fit | declare-environment | execute | doctor
python -m medos_trainer doctor      # корректно отказал: нет GPU и нет build-stamp
```

Рабочие сценарии «из коробки»:

| Сценарий | Как | Статус |
|---|---|---|
| Планирование nnU-Net-стиля | `medos-trainer plan --run-dir <dir>` → fingerprint (`plans.json` verbatim), авто-выбор архитектурного пресета по **наблюдаемому** VRAM (`architectures.select`, `backend.derive_plan`) | Работает; e2e — `tests/integration/test_trainer_fits_a_model.py` (GPU, помечен `slow`) + замеры в README §8 (RTX 4070, run PENDING→SUCCEEDED за 162 с) |
| Обучение | `medos-trainer fit --run-dir <dir>` — masked-трейнер `nnUNetTrainerMaskedChannels`, region mode, frozen plan | Работает; e2e тот же. Юниты: loss, checkpoint-метрика, determinism |
| TorchScript + ONNX + MONAI-bundle + modelcard/1 | `packaging.torchscript_bytes` / `onnx_bytes` / `write_candidate_bundle` / `write_modelcard` | Юниты есть (bundle round-trip через `medos.sdk.bundle.verify`, card читается `ModelCard.load` — `tests/test_modelcard.py`). **`onnx_bytes` тестами не покрыт** |

| Оценка | `tools/ab_evaluate.py {measure,cases,curve,clinical,reselect,compare}` — sliding-window через `nnUNetPredictor`, FROC, bootstrap-ДИ | 70 тестов `test_ab_evaluate.py` + smoke `test_clinical_assembly_smoke.py` |

Что **не** покрыто тестами: ONNX-экспорт, `execute` (supervisor), staging реальных NIfTI (e2e только на compose-стеке с GPU).

## 2. Рутина и типовые задачи — снимает ли фреймворк?

**Снимает, и местами лучше nnU-Net:**
- Планирование: fingerprint → план → препроцессинг nnU-Net штатными API, freeze плана двумя процессами (`MOS-TRAIN-135`), план из FIT-партиции только, `splits_final.json` из замороженного платформенного сплита (а не хэш nnU-Net).
- Воспроизводимость: семена + cuBLAS workspace + TF32 + `dataloader_worker_base`, «applied, not asserted», записано в `result.json` (`backend.apply_determinism`, `environment.DETERMINISM`).
- Провенанс: build-stamp (commit/dirty/inventory-digest), `produced_by` в каждом результате — у nnU-Net/MONAI такого нет вообще.
- **Masked training для частично размеченных корпусов** (`masked.py`, `masked_trainer.py`) — настоящее новаторство: per-(case, channel) маска в loss и в validation-метрике, иначе неразмеченные находки учатся как background. Это целая подсистема с AST-conformance (`test_backend_conformance.py` проверяет, что `_build_loss` не строит свой лосс).
- Экспорт-экспортёр «refuses rather than substitutes» + перевод осей z/y/x→k/j/i (`packaging._AXIS_ALPHABET`) — платформенные дефекты честно задокументированы.

**Не снимает (vs nnU-Net — «голый nnU-Net» в этих местах):**
- **Нет CLI-предикта**: подкоманд `predict/infer` нет. Sliding-window инференс существует только внутри `ab_evaluate.py`. Модель вне платформы не погоняешь на новых кейсах.
- **Нет кросс-валидации и ансамблей**: ровно 1 fold (fit→train, select→val), `all` запрещён, cascade принципиально refused (`backend._configuration`). `MOS-TRAIN-227` (ensemble machinery) в этом репо нет.
- **Только single-channel CT**: `channel_names={"0":"CT"}` зашито (`backend._dataset_json`), мультиканал отказывается (`single_channel_view`), нормализация — только CTNormalization. Нет 2d/3d_lowres/multi-config выбора (только `3d_fullres` дефолт + env-override).
- **Постобработки нет** (только платформенный `medos/sdk/postprocess.py` на сервинге).
- Метрики обучения — штатный nnU-Net pseudo-Dice; «клинические» метрики (FROC, HD95, объёмы, bootstrap-ДИ) — внешними тулзами, не в цикле обучения.

## 3. Сценарий стороннего исследователя

С датасетом КТ в nnU-Net-структуре **до обученной модели не дойти без платформы**: единственный вход — `--run-dir` с `request.json`, `preprocessing.json` (валидный `PreprocessingSpec`!), `cohort/{fit,select}.jsonl`, `images/`. Нужно самостоятельно собрать run-dir и написать PreprocessingSpec, плюс для `execute` — Postgres. Документировано это только через контракт (`medos/sdk/contract.py`, README §3) и спеку `docs/spec/17-training-pipeline.md` (1599 строк). `medos/tools/ingest/nnunet_dataset.py` существует, но пишет `supervision.json` вне этого пути. **Нет**: `trainer/examples/`, getting-started, `pyproject.toml` у `medos_trainer` (образ работает через `PYTHONPATH`), pip-пакета «фреймворка». README при этом отличный — но он про позиционирование внутри MedOS, не про внешнее использование.

## 4. Путь модели в Core

Целен и покрыт: `fit` → `bundle/` (TorchScript `models/model.ts`, golden fixture, checkpoint) + `modelcard.json` (формат `medlange.modelcard/1`) + `model.onnx` рядом → `medos/tools/deploy_model.py` (refuses: нет ONNX / digest mismatch / fixture mismatch) → Triton repo (`medos.inference.repository.write_model_directory`, config.pbtxt, warmup из golden fixture). Читатель SDK — `medos.sdk.modelcard.ModelCard.load/chain()`. «И не только»: bundle — стандартный MONAI Bundle (`configs/inference.json` генерируется как данные, target MONAI 1.4.0), ONNX — portable, dynamic batch. Но: ONNX-экспорт опционален (`ImportError` → только bundle), эквивалентность TS↔ONNX — работа ConversionRun, не тренера; `deploy_model` принимает лишь `(1,)` batch до тех пор.

## 5. Завершённость parked-модулей

- `plan.py`, `port.py`, `training.py` — **рабочая часть продукта**: их импортируют закоммиченные `backend.py`/`__main__.py` (Plan-валидация конфигурации, `port.resolve`, `FitResult`), 58+ тестов.
- `nets.py` (обёртки SegResNetDS/SwinUNETR/UNETR под calling convention nnU-Net, отказ от `compute_conv_feature_map_size` для трансформеров, pinned-замеры активаций), `detection.py` (FROC-кандидаты), `overlap.py` (Dice/HD95/ASSD/объёмы), `evidence.py` (реестр метрик + patient-cluster bootstrap) — **зрелый код с сильными тестами** (121 тест), заведён в `requirements.txt` (monai==1.5.2) и `tools/ab_evaluate.py`.
- **Но `architectures.apply_overlay` не прибит ни к одному CLI/config-пути** — только тесты зовут его. Из образа SwinUNETR/UNETR/SegResNetDS **невозможно выбрать** ни env-var, ни полем request. Это половина интеграции, а не мусор.
- **CI-дефект (проверено симуляцией)**: unit-job ставит только `pip install -e ".[dev]"` (в extras нет torch/nnunetv2/monai), а затем гоняет `pytest ... trainer/tests --require-stack` → **5 collection errors** (`test_nets`, `test_backend_conformance`, `test_checkpoint_metric`, `test_nnunet_internals`, `test_architecture_catalogue`) — и на HEAD тоже (`test_checkpoint_metric` импортирует `masked_trainer` на верхнем уровне). Тезис README «tests run with no repository around them» верен лишь на машине с зависимостями образа. Ruff на trainer намеренно не натравлен (register entry 123, 17 findings).
- **README протух против новой работы**: «four modules, 54 tests» (реально 16 модулей, 417 тестов); gap #4 «`framework_versions.monai` is absent» (monai уже в requirements); §8 замеры на nnU-Net 2.5.1/torch 2.5.1 при пинах 2.6.4/2.7.1+cu128.

## 6. Вердикт

**Как фреймворк-«аналог nnU-Net/MONAI»: 4.5–5/10. Как компонент MedOS: 7.5–8/10.**
Пайплайн обучения работает end-to-end и доказан (GPU e2e + замеры), но как фреймворк это узкая, spec-driven производная nnU-Net: только КТ single-channel, только segmentation/label, один backend, нет predict/кросс-валидации/ансамблей/cascade, вход только через платформенный run-dir, нет внешнего UX и пакетирования. Ценность — не «ускорение типовых архитектур», а governance/provenance, masked-training и клинически-осмысленная оценка, где nnU-Net и MONAI слабы.

**Топ-5 доработок:**
1. **Довести overlays до пользователя**: поле в `RunRequest`/`budget` или `MEDOS_TRAINER_OVERLAY`, вызов `apply_overlay` в `backend.derive_plan`, тест через run-dir. Файлы: `trainer/medos_trainer/backend.py`, `architectures.py`, `medos/medos/sdk/contract.py`.
2. **Автономный вход**: `medos-trainer plan --dataset <nnUNet_raw>` или генератор run-dir (`trainer/tools/make_run_dir.py` + `trainer/examples/`), чтобы исследователь без платформы дошёл до модели. Файлы: `trainer/medos_trainer/__main__.py`, новый модуль staging'а.
3. **Починить CI**: `pip install -r trainer/requirements.txt` (или extra `[trainer]`) в unit-job + `importorskip`/skip-taxonomy для 5 модулей. Файлы: `.github/workflows/tests.yml`, `pyproject.toml`, `trainer/tests/test_*.py`.
4. **Подкоманда `predict`** (nnUNetPredictor, sliding window, вывод в формате обмена) — закрыть инференс-половину вне платформы, переиспользовав проводку из `tools/ab_evaluate.py`. Файлы: `trainer/medos_trainer/__main__.py`, новый `predict.py`.
5. **Привести документацию к реальности**: README (модули/тесты, monai, пины, замеры), документирование `tools/ab_evaluate.py` и статуса overlays («implemented, not wired»). Файлы: `trainer/README.md`, новый `trainer/docs/`.

## 7. Сравнение с nnU-Net / MONAI (коротко)

| Ось | medos-trainer | nnU-Net v2 | MONAI |
|---|---|---|---|
| Автоконфиг | fingerprint + план + пресеты по VRAM — как у nnU-Net, плюс запись «почему эта архитектура» | да, эталон | Auto3DSeg — отдельный, отвергнут здесь обоснованно |
| Модальности/каналы | только single-channel CT | любые | любые |
| Кросс-валидация/ансамбли/cascade | нет (1 fold, cascade refused) | 5-fold, ансамбли, cascade — из коробки | через Auto3DSeg |
| Частичная разметка (multi-corpus) | **masked region training + masked validation — лучше nnU-Net** | ignore-label CE с кривой нормировкой (сами это документирут) | нет |
| Инференс | нет CLI (только оценочный тул) | `predict_from_raw_data`, Triton-подобный экспорт | bundles, Triton |
| Архитектуры | nnU-Net планеры + 3 MONAI-оверлея (недоведены до CLI) | 4 пресета планеров | весь зоопарк, но не plan-driven |
| Метрики/оценка | **lesion-level FROC, HD95/ASSD/объёмы, patient-cluster bootstrap ДИ, реестр ids** — сильнее обоих | Dice-centric pseudo-metric | базовые |
| Провенанс/воспроизводимость | **build-stamp, freeze плана, determinism record — сильнее обоих** | слабо | слабо |
| Портативность артефакта | MONAI Bundle + modelcard + ONNX + Triton deploy | nnU-Net checkpoint | MONAI Bundle |

Итог: это не «аналог nnU-Net», а **дисциплинированный nnU-Net-наследник с уникальной маскировочной подсистемой и evidence-слоем**, доведённый до продукта внутри MedOS, но пока недоведённый до фреймворка для внешнего пользователя. Ничего не менял.
