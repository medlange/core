# Audit of `trainer/` (medos-trainer) as a standalone product

## 0. Repository state — the key fact

The entire "framework" layer is **uncommitted** (parked peer-session):

- **Tracked (commits up to `e587315`)**: `backend.py`, `masked.py`, `masked_trainer.py`, `packaging.py`, `environment.py`, `stamp.py`, `__main__.py`, `Dockerfile`, 3–4 test files.
- **Untracked (new work)**: `plan.py`, `port.py`, `nets.py`, `detection.py`, `overlap.py`, `evidence.py`, `architectures.py`, `training.py`, `tools/ab_evaluate.py`, `tests/fixtures/`, 12 new test files, `LICENSE`.

Verdict on "dead code": **there is no dead code, but integration is uneven** (see §5).

## 1. What actually works

**I ran it myself** (Windows, `.venv` with torch 2.7.1+cpu, nnunetv2, monai 1.5.2):

```
cd trainer && pytest tests          # 417 passed in 59.58s, 0 skips
python -m medos_trainer --help      # plan | fit | declare-environment | execute | doctor
python -m medos_trainer doctor      # correctly refused: no GPU and no build-stamp
```

Working out-of-the-box scenarios:

| Scenario | How | Status |
|---|---|---|
| nnU-Net-style planning | `medos-trainer plan --run-dir <dir>` → fingerprint (`plans.json` verbatim), auto-selection of the architectural preset by **observed** VRAM (`architectures.select`, `backend.derive_plan`) | Works; e2e — `tests/integration/test_trainer_fits_a_model.py` (GPU, marked `slow`) + measurements in README §8 (RTX 4070, run PENDING→SUCCEEDED in 162 s) |
| Training | `medos-trainer fit --run-dir <dir>` — masked trainer `nnUNetTrainerMaskedChannels`, region mode, frozen plan | Works; same e2e. Units: loss, checkpoint metric, determinism |
| TorchScript + ONNX + MONAI-bundle + modelcard/1 | `packaging.torchscript_bytes` / `onnx_bytes` / `write_candidate_bundle` / `write_modelcard` | Units exist (bundle round-trip via `medos.sdk.bundle.verify`, card read by `ModelCard.load` — `tests/test_modelcard.py`). **`onnx_bytes` is not covered by tests** |
| Export to Triton (Core) | `python medos/tools/deploy_model.py --modelcard <run-dir> --repo <repo>` | Covered by `tests/unit/test_deploy_model.py` (refusals: no ONNX, digest mismatch, fixture mismatch) |
| Evaluation | `tools/ab_evaluate.py {measure,cases,curve,clinical,reselect,compare}` — sliding window via `nnUNetPredictor`, FROC, bootstrap CI | 70 tests `test_ab_evaluate.py` + smoke `test_clinical_assembly_smoke.py` |

What is **not** covered by tests: ONNX export, `execute` (supervisor), staging of real NIfTI (e2e only on a compose stack with GPU).

## 2. Routine and typical tasks — does the framework remove them?

**It does, and in places better than nnU-Net:**
- Planning: fingerprint → plan → preprocessing via stock nnU-Net APIs, plan frozen by two processes (`MOS-TRAIN-135`), plan from the FIT partition only, `splits_final.json` from the frozen platform split (not the nnU-Net hash).
- Reproducibility: seeds + cuBLAS workspace + TF32 + `dataloader_worker_base`, "applied, not asserted", recorded in `result.json` (`backend.apply_determinism`, `environment.DETERMINISM`).
- Provenance: build-stamp (commit/dirty/inventory-digest), `produced_by` in every result — nnU-Net/MONAI have nothing like this at all.
- **Masked training for partially annotated corpora** (`masked.py`, `masked_trainer.py`) — genuine innovation: a per-(case, channel) mask in the loss and in the validation metric, otherwise unannotated findings get learned as background. This is a whole subsystem with AST-conformance (`test_backend_conformance.py` checks that `_build_loss` does not build its own loss).
- The export-exporter "refuses rather than substitutes" + z/y/x→k/j/i axis translation (`packaging._AXIS_ALPHABET`) — platform defects are honestly documented.

**It does not remove (vs nnU-Net — "bare nnU-Net" in these places):**
- **No CLI predict**: there are no `predict/infer` subcommands. Sliding-window inference exists only inside `ab_evaluate.py`. You cannot run the model on new cases outside the platform.
- **No cross-validation and ensembles**: exactly 1 fold (fit→train, select→val), `all` is forbidden, cascade is refused on principle (`backend._configuration`). `MOS-TRAIN-227` (ensemble machinery) is not in this repo.
- **Single-channel CT only**: `channel_names={"0":"CT"}` is hardcoded (`backend._dataset_json`), multichannel is refused (`single_channel_view`), normalization is CTNormalization only. No 2d/3d_lowres/multi-config selection (only the `3d_fullres` default + env override).
- **No postprocessing** (only the platform `medos/sdk/postprocess.py` at serving).
- Training metrics are the stock nnU-Net pseudo-Dice; "clinical" metrics (FROC, HD95, volumes, bootstrap CI) live in external tools, not in the training loop.

## 3. Third-party researcher scenario

With a CT dataset in nnU-Net structure, you **cannot reach a trained model without the platform**: the only entry point is `--run-dir` with `request.json`, `preprocessing.json` (a valid `PreprocessingSpec`!), `cohort/{fit,select}.jsonl`, `images/`. You must assemble the run-dir yourself and write a PreprocessingSpec, plus Postgres for `execute`. This is documented only through the contract (`medos/sdk/contract.py`, README §3) and the spec `docs/spec/17-training-pipeline.md` (1,599 lines). `medos/tools/ingest/nnunet_dataset.py` exists, but writes `supervision.json` outside this path. **Missing**: `trainer/examples/`, a getting-started, a `pyproject.toml` for `medos_trainer` (the image works via `PYTHONPATH`), a pip package of the "framework". The README itself is excellent — but it is about positioning inside MedOS, not about external use.

## 4. The model's path into Core

Coherent and covered: `fit` → `bundle/` (TorchScript `models/model.ts`, golden fixture, checkpoint) + `modelcard.json` (format `medlange.modelcard/1`) + `model.onnx` alongside → `medos/tools/deploy_model.py` (refuses: no ONNX / digest mismatch / fixture mismatch) → Triton repo (`medos.inference.repository.write_model_directory`, config.pbtxt, warmup from the golden fixture). The SDK reader — `medos.sdk.modelcard.ModelCard.load/chain()`. "And more": the bundle is a standard MONAI Bundle (`configs/inference.json` is generated as data, target MONAI 1.4.0), ONNX is portable, dynamic batch. But: ONNX export is optional (`ImportError` → bundle only), TS↔ONNX equivalence is the work of ConversionRun, not the trainer; `deploy_model` accepts only `(1,)` batch for now.

## 5. Completeness of the parked modules

- `plan.py`, `port.py`, `training.py` — **the working part of the product**: the committed `backend.py`/`__main__.py` import them (Plan validation of the configuration, `port.resolve`, `FitResult`), 58+ tests.
- `nets.py` (SegResNetDS/SwinUNETR/UNETR wrappers under the nnU-Net calling convention, refusal of `compute_conv_feature_map_size` for transformers, pinned activation measurements), `detection.py` (FROC candidates), `overlap.py` (Dice/HD95/ASSD/volumes), `evidence.py` (metrics registry + patient-cluster bootstrap) — **mature code with strong tests** (121 tests), wired into `requirements.txt` (monai==1.5.2) and `tools/ab_evaluate.py`.
- **But `architectures.apply_overlay` is not wired to any CLI/config path** — only tests call it. From the image there is **no way to choose** SwinUNETR/UNETR/SegResNetDS — neither via env-var nor via a request field. This is half an integration, not dead code.
- **CI defect (verified by simulation)**: the unit job installs only `pip install -e ".[dev]"` (torch/nnunetv2/monai are not in the extras), then runs `pytest ... trainer/tests --require-stack` → **5 collection errors** (`test_nets`, `test_backend_conformance`, `test_checkpoint_metric`, `test_nnunet_internals`, `test_architecture_catalogue`) — and on HEAD too (`test_checkpoint_metric` imports `masked_trainer` at top level). The README claim "tests run with no repository around them" holds only on a machine with the image's dependencies. Ruff is deliberately not pointed at trainer (register entry 123, 17 findings).
- **README has rotted against the new work**: "four modules, 54 tests" (actually 16 modules, 417 tests); gap #4 "`framework_versions.monai` is absent" (monai is already in requirements); §8 measurements on nnU-Net 2.5.1/torch 2.5.1 with pins at 2.6.4/2.7.1+cu128.

## 6. Verdict

**As an nnU-Net/MONAI-style "framework": 4.5–5/10. As a component of MedOS: 7.5–8/10.**
The training pipeline works end-to-end and is proven (GPU e2e + measurements), but as a framework it is a narrow, spec-driven nnU-Net derivative: CT only, single-channel only, segmentation/label only, one backend, no predict/cross-validation/ensembles/cascade, entry only through the platform run-dir, no external UX or packaging. The value is not "faster typical architectures" but governance/provenance, masked training, and clinically meaningful evaluation — where nnU-Net and MONAI are weak.

**Top-5 improvements:**
1. **Bring overlays to the user**: a field in `RunRequest`/`budget` or `MEDOS_TRAINER_OVERLAY`, calling `apply_overlay` in `backend.derive_plan`, a test via run-dir. Files: `trainer/medos_trainer/backend.py`, `architectures.py`, `medos/medos/sdk/contract.py`.
2. **Standalone entry**: `medos-trainer plan --dataset <nnUNet_raw>` or a run-dir generator (`trainer/tools/make_run_dir.py` + `trainer/examples/`), so a researcher without the platform can reach a model. Files: `trainer/medos_trainer/__main__.py`, a new staging module.
3. **Fix CI**: `pip install -r trainer/requirements.txt` (or a `[trainer]` extra) in the unit job + `importorskip`/skip-taxonomy for the 5 modules. Files: `.github/workflows/tests.yml`, `pyproject.toml`, `trainer/tests/test_*.py`.
4. **A `predict` subcommand** (nnUNetPredictor, sliding window, output in the exchange format) — close the inference half outside the platform, reusing the wiring from `tools/ab_evaluate.py`. Files: `trainer/medos_trainer/__main__.py`, new `predict.py`.
5. **Bring the documentation in line with reality**: README (modules/tests, monai, pins, measurements), documenting `tools/ab_evaluate.py` and the overlays status ("implemented, not wired"). Files: `trainer/README.md`, new `trainer/docs/`.

## 7. Comparison with nnU-Net / MONAI (short)

| Axis | medos-trainer | nnU-Net v2 | MONAI |
|---|---|---|---|
| Auto-config | fingerprint + plan + presets by VRAM — like nnU-Net, plus a record of "why this architecture" | yes, the reference | Auto3DSeg — separate, justifiably rejected here |
| Modalities/channels | single-channel CT only | any | any |
| Cross-validation/ensembles/cascade | none (1 fold, cascade refused) | 5-fold, ensembles, cascade — out of the box | via Auto3DSeg |
| Partial annotation (multi-corpus) | **masked region training + masked validation — better than nnU-Net** | ignore-label CE with a weird normalization curve (they document it themselves) | none |
| Inference | no CLI (evaluation tool only) | `predict_from_raw_data`, Triton-like export | bundles, Triton |
| Architectures | nnU-Net planners + 3 MONAI overlays (not wired to CLI) | 4 planner presets | the whole zoo, but not plan-driven |
| Metrics/evaluation | **lesion-level FROC, HD95/ASSD/volumes, patient-cluster bootstrap CI, registry ids** — stronger than both | Dice-centric pseudo-metric | basic |
| Provenance/reproducibility | **build-stamp, plan freeze, determinism record — stronger than both** | weak | weak |
| Artifact portability | MONAI Bundle + modelcard + ONNX + Triton deploy | nnU-Net checkpoint | MONAI Bundle |

Bottom line: this is not an "nnU-Net analog" but a **disciplined nnU-Net successor with a unique masking subsystem and an evidence layer**, brought to product maturity inside MedOS, but not yet brought to framework maturity for an external user. I changed nothing.
