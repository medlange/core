# Аудит `D:/PycharmProjects/medlange/viewer` как самостоятельного фреймворка

## Общая картина

Viewer — это ~10 500 строк ванильного JS (app.js — 5166 строк, src/ — ~30 модулей), ES-модули без сборки, WebGL2, строгий DICOMweb-клиент. Внутренний шов чистый и продуманный; но это **first-party viewer с точкой расширения для своих**, а не фреймворк для чужих. Вся «фреймворковость» сводится к одному статическому реестру (`src/core/registry.js`), потребляемому shell'ом, при этом shell обязан быть отредактирован для каждой новой контрибуции.

---

## 1. Точки расширения

Единственный шов — `src/core/registry.js:45-58`, четыре вида: `PANEL`, `TOOL`, `OVERLAY`, `ACTION`. Регистрация только статическая (импорт → `register()`), без URL-loader и динамического `import()` — осознанно, по MOS-REL-108 (`tests/test_architecture.py:186` это гейтит).

| Точка | Статус | Факты |
|---|---|---|
| PANEL | Работает, задокументирована | `mount(root)` → teardown, `slot/order/title`; shell строит секцию (`app.js:4569` `mountPanels`, `app.js:4541` `createPanelSection`); отключение через `viewer.config.json` `panels.disabled` |
| TOOL | Работает, **документация врёт** | Реальный контракт — `handlers(panel, location, commit, setPreview)` → `{onDown,onMove,onUp,onCancel}` (`app.js:3719` `armTool`, образец `src/tools/measure-tools.js:71`). А `docs/extensions.md:73-77` описывает `activate(api)`/`onPointer` — такого API не существует. Внешний разработчик, следуя гайду, сломается |
| ACTION | Работает | Кнопка в `#bar-verbs`, `ctx = { studyUid, reloadStudy }` — и только (`app.js:3519-3543`). Больше ничего из shell не достать |
| OVERLAY | **Мёртв** | `KINDS.OVERLAY` объявлен, но ни один потребитель не вызывает `contributions(KINDS.OVERLAY)` — проверил по всему дереву. Зарегистрировавший OVERLAY получит тишину. Единственный упоминание «overlay» в коде — про штатную SEG-подложку, не про реестр |
| Modes | Нет | Концепции нет ни в коде, ни в конфиге |
| Hanging protocols API | Нет | Только data-файл `protocols.json`: закрытый словарь `when` (priorOpen/modality/min-maxImageSeries) + сетка rows/cols. Замена целиком mount'ом, не добавление. Никакого назначения серий в панели, стадий, селекторов |
| Toolbar API | Нет | TOOL/ACTION падают в `#bar-verbs`; тоглы захардкожены литералом (`app.js:3554-3569`); группы/порядок/скрытие штатных кнопок не конфигурируются |
| Services / data-source API | Нет | Директории `src/services/` не существует (упоминается только в сообщении гейта). `DicomWebClient` (`src/dicom/dicomweb.js:88`) инстанцируется приватно в `app.js:117` и плагинам недоступен; документировано прямо: «панель читает state… Лезть в сеть — нельзя, seam появится отдельным решением» (`docs/plugin-template.md:89-92`) |
| Hotkeys API | Нет | Один литеральный `keydown`-обработчик (`app.js:4351-4428`). У TOOL есть `key` — без проверки коллизий (два тула на одну клавишу → побеждает последний в цикле). ACTION/PANEL клавишу повесить не могут |
| UI-компоненты для плагинов | Де-факто | Из `src/ui/*` можно импортировать `openDialog` (`src/ui/dialogs.js:44`), `icon()` (`src/ui/icons.js:100`), export-хелперы (`src/ui/export.js`) — гейт запрещает только `app.js`. Но это недокументированный internal, без обещания стабильности |
| Доступ к инстансам/метаданным | Только state | Документированный уровень: `state.series` (QIDO-строки), `state.measurements`, `state.cursor`. **Недокументированный back door**: `setState({panels: [...panels]})` (`app.js:712`) кладёт в state живые panel-объекты с `frame/viewport/canvas/stack` — пиксели и метаданные DICOM достижимы, но это незафиксированный, неверсионируемый контракт |
| Жизненный цикл плагина | Минимум | Регистрация при импорте; mount/teardown у PANEL. Нет activate/deactivate, нет версионирования контракта вклада |

## 2. Сторонний разработчик: сценарий «подключил свой PACS, добавил панель»

**Что получится:**
- Настройка origin — замена `viewer-config.js` (bind mount): `dicomWebRoot`, `tenant`, `surfaceHeader`/`surface`, `productName`. Честный DICOMweb-root по умолчанию (`/dicomweb`), механически проверено (`tests/test_independence.py`).
- Своя панель — новый файл + **одна строка импорта в app.js** + ключи в 13 файлах `i18n/*.json` (parity-гейт не даст забыть) + pytest-гейт. Гайд `docs/getting-started.md` это реально проводит за 30 строк, и `tests/test_plugin_template.py` прогоняет код из гайдов по тем же гейтам — сильнейшая практика, доки не протухают незаметно.
- Свой инструмент — модуль + регистрация TOOL (но по неверной документации, см. выше).

**Что сломает первым (по порядку):**
1. **Transfer syntax.** Клиент требует `transfer-syntax=1.2.840.10008.1.2.1` в каждом retrieve (`src/dicom/dicomweb.js:14-31`, 406 → `transcode_refused`). Кодека в viewer нет (осознанно, ADR BUILD_VS_ADOPT). Реальный PACS с JPEG-LS/J2K/HTJ2K → viewer отказывает, пока origin не умеет транскодировать. Для «любого PACS» это блокер №1, и в README/docs он задокументирован только в шапке `dicomweb.js`, не в гайдах.
2. **Аутентификация.** `authHeaderProvider` есть в конструкторе клиента, но shell его **не передаёт** (`app.js:117-121`), и в `viewer-config.js`/`viewer.config.json` нет поля для токена. Защищённый PACS доступен только через credentials-by-proxy (nginx inject) — README это честно описывает, но «просто укажи URL» не работает.
3. **Правка ядра как норма.** Импорт в `app.js` — это edit шелла; гейт `test_every_registered_contribution_module_is_imported_by_the_shell` (`tests/test_architecture.py:559`) буквально *требует* правки ядра. Обновление на новую версию viewer'а = разрешение конфликтов в чужом 5166-строчном файле. Формально «не правя ядро» невозможно; возможно «правя ядро на одну строку».
4. **i18n**: 13 файлов на каждый ключ; `LANGUAGES` захардкожен (`src/core/i18n.js:37-51`) — новый язык = правка core.
5. Мелочь: коллизии клавиш тулов, `ai-dialog.js` как «образец ACTION» жёстко привязан к API хоста (`POST /api/v1/jobs`, `GET /api/v1/capabilities`, `cfg.apiRoot` — `src/ui/ai-dialog.js:102-135`), что противоречит README «It calls no /api/ of any kind» и делает образец непортируемым.

## 3. Конфигурация и white-label

Три слоя — хорошая идея, чётко разделены (`src/core/config.js:1-29`): `viewer-config.js` (интеграция), `viewer.config.json` (презентация), `presets.json`/`protocols.json` (данные читателя). Замена — mount поверх файла.

Есть: `productName`, `logo`/`logoGlyph` с деградацией (`config.js:142-167`), ~40 CSS-переменных темы (`--accent`, `--bg`, `--ink`… — `styles.css`), `panels.disabled`, `routing.deepLinkStudy`, tenant, consumer-header.

Не хватает для white-label: конфигурации состава/групп тулбара; ремапа хоткеев; выбора дефолтного hanging protocol; списка *включённых* панелей (только disable); мержа/добавления пресетов (только замена файла); favicon (захардкожен в `index.html:46`); футера/safety-строки (инжектится origin'ом — хост обязан делать sub_filter, это не конфиг); своих локалей; произвольных deep-link параметров (только `?study=` и `?tenant=`).

## 4. Стабильность API

Зафиксировано (и гейтится тестами): контракт `register()/contributions()`, форма PANEL mount/teardown, синхронность state, схемы `viewer.config.json` v1 (closed schema, варнинги на неизвестные ключи — `config.js:68-113`), `presets.json`/`protocols.json`.

Приватное/нестабильное: контракт TOOL (и задокументирован неверно), ctx ACTION, живые panel-объекты через `state.panels`, всё в `src/ui/*` как «компоненты», `DicomWebClient` (импортируем, но без обещаний).

Риски: нет semver на контракт вкладов, нет CHANGELOG в репо (`build.json` viewer_version 0.4.0), нет маркировки public/internal, гейты — source-grep pytest, они пинят форму только штатного дерева. Самый большой риск стабильности — сам `app.js` как точка слияния. Признаный host leak: `build.json` → `platform_version` (README «Known host leak» сам это фиксирует).

## 5. Документация

`docs/`: `extensions.md` (EN), `getting-started.md`, `plugin-template.md`, `testing.md` (RU) — **смешение языков**, для внешнего продукта это недоделка. Сильное: гайды-исполняемые-тестами, честные «чего плагин не может». Слабое:
- `extensions.md` описывает несуществующий TOOL API (выше);
- нет API-референса: форма state, поля вкладов по видам, ctx, список CSS-переменных, схемы JSON — всё это «читай исходники»;
- `apiRoot`/`capabilities` из `viewer-config.js` (использует `ai-dialog.js`) не описаны в таблице README;
- ограничение «uncompressed only» отсутствует в README/docs для интегратора;
- нет примера деплоя против стороннего PACS, нет policy версионирования/миграций.

Третьему разработчику хватит для панели-за-30-строк; не хватит для всего остального.

## 6. Вердикт

**Готовность как фреймворк для сторонних проектов: 3/10.**

Как вьювер-first-party — 7–8/10 (дисциплина DICOM-корректности редкая: photometric, padding, gantry-shear, units, truncation — каждый с измеренным дефектом и гейтом). Как фреймворк — не хватает носителя расширений (формата дистрибуции плагина), сетевого seam, data-source API, исправной документации контрактов и версионирования.

**Топ-5 доработок по приоритету:**
1. **OVERLAY: реализовать потребителя или удалить вид** — `src/core/registry.js:51` + точка в draw-цикле `app.js` (viewport/annotations). Сейчас это ложная точка расширения.
2. **Сетевой seam и data-source API**: экспортировать сконфигурированный `DicomWebClient` (или фасад) через `src/core/`; пробросить `authHeaderProvider` из `viewer-config.js` в `app.js:117` — без этого secured PACS недостижим, а панель не может сделать ни одного запроса.
3. **Убрать обязательную правку ядра**: манифест плагинов (например, `viewer.plugins.js` со списком модулей, который shell импортирует целиком) + зафиксировать контракт вкладов как версионируемый документ. Минимум — гейт на коллизии клавиш тулов.
4. **Починить `docs/extensions.md` (TOOL: `handlers(panel, location, commit, setPreview)`) и написать API-референс** (state, вклады, ctx, CSS-токены, схемы JSON) + единый язык доков.
5. **Transfer-syntax: честная интеграционная история** — явное ограничение в README/getting-started («origin обязан транскодировать в Explicit VR LE, проверьте до внедрения») + опциональный WASM-кодек за флагом конфига для white-label без правок PACS.

## 7. Сравнение с OHIF

**Где лучше:** нулевые зависимости и нет сборки (SOUP-нагрузка IEC 62304 у OHIF — огромна); ~10,5k строк против сотен тысяч — аудируемо целиком; структурные гейты + гайды-ис-доказуемые-тестами; parity 13 локалей; синхронный явный state; измеренная DICOM-корректность (MONOCHROME1, VOILUTFunction, gantry shear, padding в статистике); креденшел не в странице; конфиг-слои заменяемы mount'ом.

**Где хуже:** нет кодеков (OHIF показывает JPEG-LS/J2K/HTJ2K через WASM — здесь только uncompressed, 406); нет динамических расширений/модулей и формата пакета плагина; нет modes, нормального hanging-protocol engine, toolbar/hotkey services; нет services-шины (OHIF Commands/DataSource/UI services); нет записи измерений в DICOM SR (только localStorage, SR — read-only); нет 3D/VR; только grayscale CT/MR/PT (RGB/PALETTE refused, cine не реконструируется); нет PDF/DOC, MWL, аудита, auth-интеграции, офлайна, TypeScript-типов, экосистемы. OHIF — платформа с сообществом; это — качественный одиночный продукт с швом, который ещё предстоит превратить в платформу.
