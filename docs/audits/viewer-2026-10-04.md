# Audit of `D:/PycharmProjects/medlange/viewer` as a standalone framework

## Overall picture

The Viewer is ~10,500 lines of vanilla JS (app.js — 5,166 lines, src/ — ~30 modules), ES modules with no build step, WebGL2, a strict DICOMweb client. The internal seam is clean and well thought out; but this is a **first-party viewer with an extension point for its own team**, not a framework for outsiders. All the "framework-ness" boils down to a single static registry (`src/core/registry.js`) consumed by the shell, and the shell must be edited for every new contribution.

---

## 1. Extension points

The only seam — `src/core/registry.js:45-58`, four kinds: `PANEL`, `TOOL`, `OVERLAY`, `ACTION`. Registration is static only (import → `register()`), with no URL-loader and no dynamic `import()` — deliberate, per MOS-REL-108 (`tests/test_architecture.py:186` gates it).

| Point | Status | Facts |
|---|---|---|
| PANEL | Works, documented | `mount(root)` → teardown, `slot/order/title`; the shell builds the section (`app.js:4569` `mountPanels`, `app.js:4541` `createPanelSection`); disabled via `viewer.config.json` `panels.disabled` |
| TOOL | Works, **documentation lies** | The real contract is `handlers(panel, location, commit, setPreview)` → `{onDown,onMove,onUp,onCancel}` (`app.js:3719` `armTool`, sample `src/tools/measure-tools.js:71`). But `docs/extensions.md:73-77` describes `activate(api)`/`onPointer` — no such API exists. An external developer following the guide will break |
| ACTION | Works | A button in `#bar-verbs`, `ctx = { studyUid, reloadStudy }` — and that's all (`app.js:3519-3543`). Nothing else is reachable from the shell |
| OVERLAY | **Dead** | `KINDS.OVERLAY` is declared, but no consumer anywhere calls `contributions(KINDS.OVERLAY)` — verified across the whole tree. Whoever registers an OVERLAY gets silence. The only "overlay" mention in the code is about the built-in SEG underlay, not the registry |
| Modes | None | The concept exists neither in code nor in config |
| Hanging protocols API | None | Only the data file `protocols.json`: a closed dictionary `when` (priorOpen/modality/min-maxImageSeries) + a rows/cols grid. Replacement wholesale via mount, not addition. No series assignment to panes, stages, or selectors |
| Toolbar API | None | TOOL/ACTION fall into `#bar-verbs`; toggles are hardcoded as a literal (`app.js:3554-3569`); groups/order/hiding of built-in buttons are not configurable |
| Services / data-source API | None | The `src/services/` directory does not exist (mentioned only in a gate message). `DicomWebClient` (`src/dicom/dicomweb.js:88`) is instantiated privately in `app.js:117` and is unavailable to plugins; documented plainly: "a panel reads state… going to the network is not allowed, a seam will come as a separate decision" (`docs/plugin-template.md:89-92`) |
| Hotkeys API | None | A single literal `keydown` handler (`app.js:4351-4428`). TOOLs have a `key` — with no collision checks (two tools on one key → the last one in the loop wins). ACTION/PANEL cannot attach a key |
| UI components for plugins | De facto | From `src/ui/*` you can import `openDialog` (`src/ui/dialogs.js:44`), `icon()` (`src/ui/icons.js:100`), export helpers (`src/ui/export.js`) — the gate only forbids `app.js`. But this is an undocumented internal, with no stability promise |
| Access to instances/metadata | State only | The documented level: `state.series` (QIDO rows), `state.measurements`, `state.cursor`. **Undocumented back door**: `setState({panels: [...panels]})` (`app.js:712`) puts live panel objects with `frame/viewport/canvas/stack` into state — pixels and DICOM metadata are reachable, but this is an unrecorded, unversioned contract |
| Plugin lifecycle | Minimal | Registration on import; mount/teardown for PANEL. No activate/deactivate, no versioning of the contribution contract |

## 2. Third-party developer: the "connected my own PACS, added a panel" scenario

**What will work:**
- Origin setup — replacing `viewer-config.js` (bind mount): `dicomWebRoot`, `tenant`, `surfaceHeader`/`surface`, `productName`. Honest DICOMweb root by default (`/dicomweb`), mechanically verified (`tests/test_independence.py`).
- Own panel — a new file + **one import line in app.js** + keys in 13 `i18n/*.json` files (the parity gate won't let you forget) + a pytest gate. The `docs/getting-started.md` guide genuinely walks you through it in 30 lines, and `tests/test_plugin_template.py` runs the code from the guides through the same gates — the strongest practice; docs can't rot unnoticed.
- Own tool — a module + TOOL registration (but per the incorrect documentation, see above).

**What breaks first (in order):**
1. **Transfer syntax.** The client requires `transfer-syntax=1.2.840.10008.1.2.1` in every retrieve (`src/dicom/dicomweb.js:14-31`, 406 → `transcode_refused`). There is no codec in the viewer (deliberate, ADR BUILD_VS_ADOPT). A real PACS with JPEG-LS/J2K/HTJ2K → the viewer refuses until the origin can transcode. For "any PACS" this is blocker №1, and in the README/docs it is documented only in the header of `dicomweb.js`, not in the guides.
2. **Authentication.** `authHeaderProvider` exists in the client constructor, but the shell **does not pass it** (`app.js:117-121`), and there is no field for a token in `viewer-config.js`/`viewer.config.json`. A secured PACS is reachable only via credentials-by-proxy (nginx inject) — the README describes this honestly, but "just point it at a URL" does not work.
3. **Editing the core as the norm.** The import in `app.js` is an edit of the shell; the gate `test_every_registered_contribution_module_is_imported_by_the_shell` (`tests/test_architecture.py:559`) literally *requires* editing the core. Upgrading to a new viewer version = resolving conflicts in someone else's 5,166-line file. Formally "without editing the core" is impossible; possible is "editing the core by one line".
4. **i18n**: 13 files per key; `LANGUAGES` is hardcoded (`src/core/i18n.js:37-51`) — a new language = an edit of core.
5. Minor: tool key collisions, `ai-dialog.js` as the "ACTION sample" is tightly bound to the host API (`POST /api/v1/jobs`, `GET /api/v1/capabilities`, `cfg.apiRoot` — `src/ui/ai-dialog.js:102-135`), which contradicts the README "It calls no /api/ of any kind" and makes the sample non-portable.

## 3. Configuration and white-label

Three layers — a good idea, cleanly separated (`src/core/config.js:1-29`): `viewer-config.js` (integration), `viewer.config.json` (presentation), `presets.json`/`protocols.json` (reader data). Replacement — mount over the file.

Present: `productName`, `logo`/`logoGlyph` with degradation (`config.js:142-167`), ~40 theme CSS variables (`--accent`, `--bg`, `--ink`… — `styles.css`), `panels.disabled`, `routing.deepLinkStudy`, tenant, consumer-header.

Missing for white-label: toolbar composition/group configuration; hotkey remapping; default hanging protocol selection; a list of *enabled* panels (only disable); preset merging/addition (file replacement only); favicon (hardcoded in `index.html:46`); footer/safety string (injected by the origin — the host must do sub_filter, this is not config); own locales; arbitrary deep-link parameters (only `?study=` and `?tenant=`).

## 4. API stability

Pinned (and gated by tests): the `register()/contributions()` contract, the PANEL mount/teardown shape, state synchronicity, the `viewer.config.json` v1 schema (closed schema, warnings on unknown keys — `config.js:68-113`), `presets.json`/`protocols.json`.

Private/unstable: the TOOL contract (also documented incorrectly), ACTION ctx, live panel objects via `state.panels`, everything in `src/ui/*` as "components", `DicomWebClient` (importable, but with no promises).

Risks: no semver on the contribution contract, no CHANGELOG in the repo (`build.json` viewer_version 0.4.0), no public/internal marking, the gates are source-grep pytest — they only pin the shape of the stock tree. The biggest stability risk is `app.js` itself as the merge point. Acknowledged host leak: `build.json` → `platform_version` (the README "Known host leak" records exactly this).

## 5. Documentation

`docs/`: `extensions.md` (EN), `getting-started.md`, `plugin-template.md`, `testing.md` (RU) — **language mixing**, for an external product this is unfinished business. Strong: guides-executable-by-tests, honest "what a plugin cannot do". Weak:
- `extensions.md` describes a nonexistent TOOL API (above);
- no API reference: the shape of state, contribution fields by kind, ctx, the list of CSS variables, JSON schemas — all of this is "read the sources";
- `apiRoot`/`capabilities` from `viewer-config.js` (used by `ai-dialog.js`) are not described in the README table;
- the "uncompressed only" limitation is absent from the README/docs for the integrator;
- no deployment example against a third-party PACS, no versioning/migration policy.

A third-party developer has enough for a panel-in-30-lines; not enough for anything else.

## 6. Verdict

**Readiness as a framework for third-party projects: 3/10.**

As a first-party viewer — 7–8/10 (the DICOM-correctness discipline is rare: photometric, padding, gantry-shear, units, truncation — each with a measured defect and a gate). As a framework — missing an extension carrier (a plugin distribution format), a network seam, a data-source API, correct contract documentation, and versioning.

**Top-5 improvements by priority:**
1. **OVERLAY: implement a consumer or remove the kind** — `src/core/registry.js:51` + a hook in the draw loop `app.js` (viewport/annotations). Right now it is a false extension point.
2. **Network seam and data-source API**: export the configured `DicomWebClient` (or a facade) through `src/core/`; pass `authHeaderProvider` from `viewer-config.js` into `app.js:117` — without this a secured PACS is unreachable, and a panel cannot make a single request.
3. **Remove the mandatory core edit**: a plugin manifest (e.g. `viewer.plugins.js` with a list of modules that the shell imports wholesale) + pin the contribution contract as a versioned document. Minimum — a gate for tool key collisions.
4. **Fix `docs/extensions.md` (TOOL: `handlers(panel, location, commit, setPreview)`) and write an API reference** (state, contributions, ctx, CSS tokens, JSON schemas) + a single documentation language.
5. **Transfer syntax: an honest integration story** — an explicit limitation in README/getting-started ("origin must transcode to Explicit VR LE, verify before rollout") + an optional WASM codec behind a config flag for white-label without PACS changes.

## 7. Comparison with OHIF

**Where better:** zero dependencies and no build step (the IEC 62304 SOUP load of OHIF is enormous); ~10.5k lines versus hundreds of thousands — auditable in full; structural gates + guides-provable-by-tests; 13-locale parity; synchronous explicit state; measured DICOM correctness (MONOCHROME1, VOILUTFunction, gantry shear, padding in statistics); credentials not in the page; config layers replaceable by mount.

**Where worse:** no codecs (OHIF shows JPEG-LS/J2K/HTJ2K via WASM — here only uncompressed, 406); no dynamic extensions/modules and no plugin package format; no modes, no proper hanging-protocol engine, toolbar/hotkey services; no services bus (OHIF Commands/DataSource/UI services); no writing of measurements to DICOM SR (localStorage only, SR is read-only); no 3D/VR; grayscale CT/MR/PT only (RGB/PALETTE refused, cine not reconstructed); no PDF/DOC, MWL, audit, auth integration, offline, TypeScript types, ecosystem. OHIF is a platform with a community; this is a quality single product with a seam that still has to be turned into a platform.
